# AI bridge：進度紀錄與未來規劃

> 寫於 2026-10-16，最後更新同一天。分支是 `ai-bridge`，從 OpenPnP 的 `5bd404cf` 開始。
> 每天的細節在 [worklog/](../worklog/)，最初的計畫在 [AI_BRIDGE_PLAN.md](AI_BRIDGE_PLAN.md)。

## 1. 原則：能用腳本的就用腳本，腳本失敗時才由 AI 接手

- **腳本（程式）負責**：固定的流程，以及有明確判斷標準的事情。例如：讀 QR、找料帶孔、量 Z、底部視覺、放料、比對放置前後的照片、判斷合格與否。這些都不花 token，每次結果都一樣。
- **AI 負責**：
  1. 腳本回報失敗或無法判斷時，看照片、找原因（例如定位孔和背景連在一起、標籤被切到、料帶放反、拿錯料）。
  2. 修改程式或調整參數，並記錄下來。
  3. 抽查：偶爾看幾張照片，確認腳本的判斷還是準的。
- 所以每支腳本都要做到兩件事：**輸出結構化的結果**（狀態、原因、數值），並且**把照片存檔**（`ai-bridge/inspect/`、`scan/`、`captures/`）。這樣 AI 接手時，不用重新移動機器就能查原因。

## 2. 已完成的功能：依流程分類

### 頻率代號

越下面的頻率越高，越需要做成腳本。

| 代號 | 多久做一次 |
|---|---|
| **M** | 每台機器一次（或改硬體時） |
| **P** | 每種封裝一次（例如 C0603 調一次，所有 0603 電容都適用） |
| **R** | 每捲料、每次換料或移動料帶 |
| **J** | 每種板子（每個 job）一次 |
| **B** | 每批板子（每次放上新板） |
| **N** | **每顆零件**（每次放料） |
| **E** | 出錯時 |

### 2.10 Token 用量分析

`python ai-bridge/token_usage.py [session.jsonl] [--since 時間]` 會讀取 Claude Code 的對話紀錄（`~/.claude/projects/<專案>/*.jsonl`），把每次呼叫模型的用量分攤到各個工具上：
- 工具結果算在下一次呼叫的「新輸入」裡。
- 模型呼叫工具時寫出的內容算在「輸出」裡。

2026-10-12 到 10-16 這個對話（873 次呼叫）的結果：

| 工具 | 平均每次（token） |
|---|---|
| `get_status`、`home_machine` | 300–450 |
| `place_from_job` | 約 1,100 |
| `scan_qr_feeders`、`probe_feeder_z` | 約 1,000 |
| `test_bottom_vision`（3 張照片） | 約 3,200 |
| `inspect_placements`（附照片時） | 約 3,800 |
| `list_job_placements`（88 個 placement） | 約 16,000 |

- 總計：新輸入 295 萬、輸出 68 萬、**讀快取 2.67 億**。每次呼叫都會把整段對話重新讀一遍，讀快取單價雖然只有新輸入的約十分之一，但換算下來仍然是新輸入的 9 倍左右。
- 所以：**最貴的不是單一工具，而是由 AI 一步一步呼叫、把對話越拉越長。** 用腳本跑完整個流程，是省最多的方法。另外，一個任務做完就開新對話（`/clear`）。
- 實測（10/16，4 片各放一顆 C6 並驗收）：`run_job.py` 是 1 次 Bash 呼叫，摘要約 400 token、1–2 次模型請求；AI 逐步呼叫要 `list_job_placements`（16k）＋ place／inspect 各自的 plan 和執行（約 6–10k）、6–8 次請求，每次再重讀整段對話的快取。差 10 倍以上。

## 3. 已知問題與發現

| 問題 | 影響 | 目前處理 |
|---|---|---|
| 歸零撞到限位開關時機器會震動，沒有錫膏的零件會跳開（不是每次都會） | 乾放測試時，放好的零件可能移位 | 放好零件後盡量不要重啟或歸零；要重啟就先檢查一次 |
| 真機版 OpenPnP 偶爾關不掉（`quit()` 中途出現例外） | 要強制結束 | 10/16 查到：OpenPnP 在跑時重新建置了 jar，關閉時 `NoClassDefFoundError`。先關閉再建置 |
| ~~真空感測只讀 MSB（256 階），N045 有零件和沒零件只差 3–4 階~~ | 量 Z、判斷有沒有吸到零件都不太靈敏 | 10/16 已修：`M261 A109 B2 S2` 讀兩個位元組，空的 −6560、有零件 −7180～−7520；N045 開了吸取後的真空檢查 |
| 吸嘴頭都沒有開吸取後的真空檢查 | 吸起來沒有、拋料成功沒有，程式都不知道 | 10/16：N045 已開吸取後的檢查（−6900）；放置後的檢查和其他吸嘴頭還沒開 |
| N045 有偏擺（runout），也沒做吸嘴頭校準 | 零件轉角度時偏移會變 | 底部視覺在最終角度拍照，所以還能修正 |
| 上相機是固定焦距，標籤比板面高，所以會失焦 | QR 還讀得出來 | 不用處理 |
| 上相機的視野在 Y 方向只有 10.6 mm | 標籤要排得夠整齊 | 掃描改拍 5 排，可容許 ±4 mm |
| 很靠近定位孔剪的料帶，孔會跟底板連在一起 | 找不到定位孔 | 已修正（先用 opening 切開） |
| 放置有系統性偏移：10/16 的 4 顆 C6 都是 X +0.06～+0.10、Y −0.14～−0.19 mm | 在容許值 0.25 內，但吃掉一半餘裕 | 待查：吸嘴頭偏移、底部相機位置或上相機偏移的校正 |
| 電腦斷電重開機後，相機曝光變成設定檔的 −1（最亮）：底部視覺框到吸嘴反光、驗收量錯 | 10/16 晚上整批 C6 被擋下 | 10/16 已修：曝光改回 Top −4、Bottom −5，開啟 freeze（每次開相機都套用）；新增 `camera_properties` |
| 小零件（0603）的角度量測有幾度雜訊 | 誤判成 `check` | 改成用末端位移判斷，**還沒在真機上驗證** |
| `update_feeder` 改 strip feeder 的 Z 時，送料計數也被重設，回到第一格（10/29） | 掃描後再改 Z，feeder 會去吸已經用掉的空格，`No part vacuum-detected` | 待修：改 Z 時保留 feed count。暫時：改完 Z 再跑一次 `scan_qr_feeders(apply)` |
| `place_from_job` 遇到吸取失敗（`No part vacuum-detected`）整批停下，不會只停用那個 feeder 繼續放別的（10/29） | 一條料帶用完，其他料也不放了；四片板子要重下 6 次指令 | 待修：吸取失敗時停用那個 feeder、繼續放其他零件，最後列出缺的 |
| 空板比對會把旁邊新放的零件算成「已經有零件」（10/29，變化 0.3–1.7 mm²） | 鄰近 2–3 mm 的 placement 被跳過（一次 10 顆） | 暫時：分批放之前重拍那些 placement 的空板照片。待修：只比對焊墊範圍，或用放料前那張照片比對 |
| 相機的 USB 裝置路徑會自己改變（沒有序號），上下相機也可能對調；接反時 fiducial 歸零還是可能「成功」 | 找不到相機就無法歸零；接反時座標可能偏掉 | 10/16 已在 Java 端處理：找不到記錄的路徑時自動改用剩下的同型號相機；bridge 歸零後檢查上相機畫面會跟著噴頭移動。兩台都換路徑時還是可能接反，由歸零檢查抓到，再用 `fix_cameras.py --swap` |

### 4.2 改成腳本自動跑（不需要 AI）

目標：一個人放好板子和料帶，執行一個指令就能跑完；只有失敗時才找 AI。

1. ✅ **`run_job.py`**（10/16，真機 4 顆 C6 一次通過，51 秒）：完整流程的腳本。
   - 換新板子時先跑空板拍照（`survey_bare_boards`）。
   - 依零件高度排序，**先放矮的，再放高的**（用零件的 `height`，所以要先補齊高度是 0 的零件）。
   - 放料，再驗收（`inspect_placements`，預設只回傳不合格的照片）。
   - 輸出一份報告：每個 placement 的判定、不合格的照片路徑、被停用的 feeder、用掉的零件數。
2. ✅ **`tune_bottom_vision.py`**（10/16，真機 10nF：170/180 被大小檢查擋、190–250 通過、選 220、−90° ok）：把今天手動調門檻的方法寫成腳本。通過＝找到 + 大小檢查 ok + 角度離中位數 2° 內；取最長連續範圍的中間值，`--apply` 寫入零件或封裝（`--package`）。原本的說明：從高到低掃一遍門檻，找出「量到的大小接近 footprint、角度穩定」的範圍，取中間值，有需要時再建立該封裝的視覺設定。結果不確定時（例如找不到可用範圍）才交給 AI。
3. ✅ **`scan_feeders.py --verify`**（10/16）：新增的 feeder 接著自動量 Z（接觸 −0.1）、試吸、底部視覺（含大小檢查）、拋掉，全部通過才啟用；`--verify-all` 連更新的也驗。真機：100nF、10nF 通過；1uF 因為上膜沒撕完被抓到。待加：認出上膜（反光），掃描時就略過。
4. ✅ **所有腳本統一的回報格式**（10/16，`ai-bridge/report.py`）：`run_job`、`scan_feeders`、`tune_bottom_vision` 每次動到機器都寫 `ai-bridge/reports/<時間>-<腳本>/report.json`：status、message、args、失敗時的吸嘴狀態，以及經驗庫裡症狀相符的條目（`hints`）。AI 接手時從這裡讀。

### 4.4 介面大改

**目標**：介面只留下人一定要看、一定要做決定的東西，其他參數都收進預設收合的「進階」層級。需要時人還是可以展開來調。

**一定要給人看的**

| 項目 | 原因 |
|---|---|
| 選擇或上傳電路板檔案、job | 只有人知道要做哪一片板子 |
| 板子放好之後的預覽照片（含基準點） | 確認板子放對了、方向正確 |
| 料帶和 feeder 的對應表（QR 掃描結果）、缺料、拿錯料、料帶放反 | 這些都要人動手處理 |
| 開始、暫停、停止 | |
| 安全提醒：歸零前確認路徑淨空，零件放好後會不會被震走 | |
| 結果報告：合格、需檢查、缺件的數量，以及**只有不合格的照片** | 人要決定要不要重放 |
| 需要人處理的錯誤：換料、拿走零件、吸嘴上還有零件 | |

**預設收合，人不用看的（進階）**

- 視覺 pipeline、門檻、各封裝的視覺設定
- feeder 座標、Z、rotation in tape、送料間距
- 吸嘴頭、真空門檻、Safe Z、相機校正、Gcode
- 驗收的容許值（0.25 mm）、比對參數

**做法**

- OpenPnP 原本的介面（Swing）全部保留，進階使用者照常可以用。
- 簡化版介面有兩個選擇：
  - **A. 本機網頁**：由 bridge 在 127.0.0.1 提供，畫面的內容直接用 bridge 的 HTTP API 取得。改版快、手機或平板也能看。
  - **B. OpenPnP 裡新增一個「簡易」分頁**（Swing）。
  - 我建議 **A**：bridge 已經有所有需要的 API，網頁版本比 Swing 好改。
- 全景圖也一起整合進去（之前延後的項目）。
